# 需求驱动代码验收工作流（v4.3）

## 目标与通过标准

功能需求、原生成提示词和 AI 代码分别输入，验收输出必须同时回答：

1. 当前实现是否满足本轮已认可检查？显示失败、范围内通过或无法判定。
2. 依据是什么？每个动态案例保留输入、固定断言、实际观察、需求编号和证据编号。
3. 如何改进？功能缺陷建议引用真实反例；静态质量问题引用规则和代码位置；
   提示词诊断列出覆盖、遗漏、冲突与改写后的文本。
4. 修改后是否改善？复用同一确认标准重新执行，比较代码变化前后的结果。

确认标准时，用户核对的是本轮要运行的用例及其预期结果。通过结论只覆盖这些用例。
确认之前不执行候选代码；修改需求或函数入口必须重新确认，
修改代码和生成提示词可以复用标准。模型不能产生用户确认记录或执行证据。

## 操作

1. 启动 Docker Desktop，在仓库根目录执行：
   `powershell -ExecutionPolicy Bypass -File scripts/start.ps1 -Install`。
   脚本创建独立 `.venv`，安装依赖并准备 `python:3.10-slim` 镜像。
2. 如需模型能力，启动前设置 `DEEPSEEK_API_KEY`，或写入根目录 `.env`。
   “模型已配置”仅表示存在配置，连接在实际调用时验证。
3. 打开 `http://127.0.0.1:8000/acceptance.html`，输入需求、提示词、代码和函数名。
4. 点击“生成验收标准”，核对需求及案例。模型未配置时可点击“手动填写测试”。
   例如 `add(a,b)` 的位置参数填 `[2,3]`、返回值期望填 `5`。
   列表作为单一参数时填 `[[3,1,2]]`；字符串参数填 `["AEIOU"]`。
5. 可以直接修改表中的输入与期望，添加案例，或在完整计划编辑区修订
   必要/可选需求、澄清问题、契约和关键字参数。未决歧义必须先澄清。
6. 核对后勾选确认，再点击“确认标准”“开始验收”。
   页面明确采用固定案例范围：完整输入输出或异常案例可以作为这些输入上的标准，
   不把模型的“必要条件”标签提升成整个输入域上的充分性证明。
   只有 ORDERED、返回类型等部分性质时仍拒绝功能通过，必须补充完整预期。
7. 查看结论、案例证据、代码质量建议与提示词改写。修改代码后直接再次验收，
   界面显示相同标准下的前后结果。报告可下载为 JSON。

页面提供元音统计、整数范围限制、保留重复元素排序三组正确/错误实现及独立期望值。
可先验收错误实现，再点击“换入示例正确实现”验证相同标准下能通过。

## 判定

- 必要需求的认可检查出现有效失败证据：`FAIL`。
- 必要需求有充分/等价契约，认可案例全部执行通过，规格符合确认策略：
  `PASS_WITHIN_SCOPE`，保证等级只为 `TESTED`。
- 未确认的语义、只有部分性质、缺案例、超时、协议异常、环境阻断：
  `INCONCLUSIVE`，不得把未执行当作通过。
- 语法错误由编译器证据直接判失败，并给出编译器行号及修正建议。
- 显示通过比例，但不以比例阈值替代需求判定。
- 静态质量与功能结果同时报告：一般质量问题给建议；
  高严重度安全规则触发 `REVIEW_REQUIRED`，不会被功能测试通过遮盖。

## 证据与建议

代码建议模型收到完整失败案例及已通过案例的输入、断言和观察。
建议中的输入、期望、实际、证据编号由系统用本轮真实记录填入，模型不能改写这些事实。
借用通过案例、其他需求或不存在证据的“确认缺陷”会降级为待验证风险。
模型遗漏的真实缺陷由规则建议补全。建议中的修改本身仍需回归验证。

提示词改写以需求为依据，与代码结论分别计算：
提示词有冲突时，正确代码仍可通过；提示词正确也不能掩盖代码反例。
用户可以用新提示词重新生成代码，再按原计划比较前后结果。
模型不可用时，系统采用文本匹配，并保留用户的原提示词。

## API

| 方法与路径 | 用途 |
| --- | --- |
| GET `/api/acceptance/environment` | 模型配置、Docker/镜像状态及处理办法 |
| GET `/api/acceptance/demos` | 仓库中的可复核演示需求、代码和案例 |
| POST `/api/acceptance/prepare` | 接收 EvaluationRequest，生成可编辑 spec/plan/审查意见；不执行代码 |
| POST `/api/acceptance/confirm` | 接收 requirement/entrypoint/spec/plan/scope_note/confirmed=true，结构校验后保存新确认版本；显式 case_scope_confirmed=true 表示只按确认的固定完整案例验收 |
| POST `/api/acceptance/evaluate` | 在 acceptance_materials 提供 confirmed_spec_id 与 confirmed_spec_hash，执行并生成报告 |

确认记录在 `data/acceptance_standards/`；每次修订产生新 ID。
报告与原始执行工件在 `data/acceptance_artifacts/<evaluation_id>/`。
规格、计划与代码分别计算摘要，防止跨版本复用证据；需求和入口与确认记录绑定。

## 可重复验证

```powershell
.venv/Scripts/python.exe -m pytest tests/ -q
.venv/Scripts/python.exe scripts/verify_workflow.py
.venv/Scripts/python.exe scripts/verify_workflow.py --live-model --out data/workflow_live
```

验证脚本默认使用真实 Docker，检查错误代码失败、正确代码通过、建议绑定证据及同一计划摘要。
`--live-model` 额外要求真实模型诊断出示例提示词冲突并给出改写。
默认离线测试不访问模型；mock 与真实 Docker/模型记录应区分。
仅运行可信示例可显式加 `--local-demo`。

## 范围

支持可调用 Python 函数（含 async）及少量辅助 Python 文件，输入输出以 JSON 值为协议。
提供固定返回值、None、异常、输入不变、元素性质、顺序、多重集、返回类型与标量谓词检查。
完整 Web/GUI/数据库应用需要额外集成环境，不能据函数测试声称全系统可用。
容器为无网络、只读根、非 root、1 CPU/512 MiB/64 PID 限额；超时后清理本次容器。
仍不等同于对任意恶意代码的完备防御。没有可用环境时保持阻断。
