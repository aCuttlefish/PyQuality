# PyQuality 可验证规格

《软件理论与工程》过程作业 1 · 敖德太 · 3220261332

核对重点为案例覆盖和独立预期，关注组合金额、目标运行时边界、邮箱规范化与固定计划。

## 一、概述

### 1.1 项目目标

PyQuality 面向 AI 生成的 Python 函数提供需求驱动的验收。用户输入功能需求、原提示词、候选代码和函数入口，核对并确认测试标准。系统运行候选代码，提供可追溯的判定、失败证据、静态质量发现和修改建议，并支持在同一标准下复验修改后的代码。项目用可验证的需求、真实运行和前后对照落实 SE4AI。

### 1.2 目标用户

主要用户是使用 AI 辅助实现 Python 函数、需要判断结果能否采用的学生和开发者。次要用户是课程助教或验收人员，他们需要据同一批输入和预期复查结论，并核对报告是否如实呈现了执行范围。

### 1.3 范围与边界

- **范围内**：可调用 Python 函数及必要的辅助文件。支持 JSON 可表示的输入输出，确认固定案例后的功能验收、静态检查、基于证据的代码建议、提示词诊断和同标准复验。
- **范围外**：完整 Web、GUI、数据库应用的端到端验收，覆盖整个输入域的形式化证明，自动应用修复，以及提示词改写对所有模型或任务的成功率保证。

## 二、功能需求与验收标准

执行前固定样本、预期和项目版本。实际执行人可以是任一组员或验收教师。文中的案例路径以提交目录为起点，自动化用例位于 `tests/`，项目样例位于 `code/samples/acceptance/`，实测原始记录位于 `eval/`。

| 编号 | 功能需求（做什么） | 验收标准（谁、怎么做、样本规模、通过条件） |
| --- | --- | --- |
| FR-01 | 用户可分别提供需求、原提示词、待验收代码和函数入口。 | 验收人从工作台加载 **1 个**元音统计样例，逐项与 `vowels.json` 对照。需求、原提示词、代码和入口 **4 项均一致**为通过。数字来自 S1 的完整输入字段。 |
| FR-02 | 用户可核对并确认固定案例，改变需求或入口后需重新确认。 | 测试人员运行 `test_confirmation_is_persisted_and_requirement_bound`、`test_changed_entrypoint_requires_new_confirmation` 和 `test_fixed_case_scope_does_not_approve_only_partial_properties`。确认记录持久化，需求变更使已执行案例数为 **0**，入口变更及仅检查部分性质分别被拒绝。**3 项均通过**。数字来自 S2 的三项回归断言。 |
| FR-03 | 系统按证据给出失败、范围内通过或无法判定。 | 验收人核对元音样例原实现、正确实现，以及 `test_blocked_env_inconclusive_not_fake_pass` 的环境阻断场景。**3 种场景全符合预期**：原实现 **4/7、`FAIL`**，正确实现 **7/7、`PASS_WITHIN_SCOPE`**，无可用执行环境且无独立失败证据时为 `INCONCLUSIVE`，执行 **0 项**。样本与预期来自 S1、S2。 |
| FR-04 | 验收报告展示失败输入、预期、实际观察及可查的证据编号。 | 验收人打开元音统计原实现报告，抽查 **1 项**大写输入 `AEIOU` 的反例。输入对应原案例，预期返回 **5**，实际返回 **0**，且可由建议中的证据编号查回同一执行记录。该反例全部满足为通过。输入及预期来自 S1。 |
| FR-05 | 系统单独报告静态质量发现和功能结果，高严重度风险提示人工审查。 | 测试人员运行 **1 项** `test_quality_advice_in_same_report_without_hiding_function_result`。给定功能输出正确、含已定义高风险规则命中的夹具，功能字段为 `PASS_WITHIN_SCOPE`，静态质量和综合可用性均为 `REVIEW_REQUIRED`，报告含相应建议。所有断言通过。样本和阈值来自 S2。 |
| FR-06 | 系统依据真实反例提出代码修改建议，区分已确认缺陷与待验证风险。 | 测试人员运行 **2 项** `test_suggestions_include_real_inputs_expected_and_actual` 和 `test_passing_evidence_cannot_be_borrowed_to_claim_defect`。建议的输入、预期、实际和证据编号与执行记录一致，引用通过记录的缺陷建议标为待验证风险。**2/2** 通过。数字来自 S2。 |
| FR-07 | 模型能力可用时，系统诊断提示词冲突并给出改写。 | 验收人审阅 `eval/workflow/` 留存的整数范围限制、保留重复元素排序和元音统计的错误实现报告。**3/3** 报告均标记真实模型模式，含 `CONFLICT` 及非空改写条目。核查留存报告与现场重新调用分别记录。样本数来自 S3 的真实模型验收子集。 |
| FR-08 | 用户可用同一已确认标准重新验收修改后的代码并取得可对比报告。 | 验收人以 **1 个**元音样例运行前后 **2 轮**，保留确认标准、只换候选代码。核对可下载报告，前后标准 ID 和计划摘要一致、代码摘要不同，实际分别为 **4/7** 和 **7/7**，两轮均执行全部 **7 项**。全部条件成立为通过。规模及预期来自 S1。 |

## 三、非功能需求与自定指标

| 编号 | 类别 | 指标承诺 | 验收标准 | 数字来源 |
| --- | --- | --- | --- | --- |
| NFR-01 | 执行隔离 | 默认动态执行采用受限容器。运行限额为 **1 CPU、512 MiB、64 个进程**。 | 测试人员核对容器启动配置中 **3 项**资源限制，再运行 **1 次**隔离检查。执行进程为非 root，根文件系统不可写，容器仅有回环网络接口，模型密钥环境变量对容器不可见。配置和观察均符合为通过。 | S4 的项目配置和实测。限额属于当前实现约束。 |
| NFR-02 | 异常恢复 | 单次任务超时有明确状态，任务容器得到清理。 | 测试人员执行 **1 次**受控超时测试，确认记录为 `TIMEOUT`，任务结束后残留容器数为 **0**。可复核记录并运行 `test_docker_timeout_cleans_up_named_container`。两项检查均满足为通过。 | S2 的回归和 S4 的真实超时记录。 |
| NFR-03 | 可复现 | 在配置好容器环境后，已留存的固定案例可以重新运行并对照。 | 验收人员按交付说明运行默认 `verify_workflow.py`。**5 个**样例各 **2 轮**，**10 份**报告的通过条数和功能结论均与 S3 对应基线一致，每对报告复用同一计划摘要。对比只要求确定性功能输出。 | S3 的三组基础演示和两组业务实验，每组含原实现及修正版。 |
| NFR-04 | 可追溯 | 过期或被改写的确认记录不能作为本轮验收标准。 | 测试人员分别制造版本摘要不匹配和已保存计划内容变化，运行 `test_confirmation_hash_mismatch_rejected` 和 `test_stored_plan_tampering_rejected`。**2/2** 被拒绝为通过。 | S2 的两项既有回归。 |

## 四、AI 使用说明

本次规格整理由组长在 Codex 中提供课程模板和项目目标。Codex 对照现有工作流、测试、固定样例和实测报告，整理了需求编号、验收方法及数字出处。案例预期和评测结果以项目已有记录为准，组内提交人应核查自己实际采用的规格文本和参与情况。项目内的模型用于辅助准备标准、诊断提示词和整理建议，标准确认由人完成，功能结论依据程序运行证据和规则。

可核查的 AI 协作过程见 `docs/AI协作与核查记录.md`。各成员的实际职责与使用记录请见各自复盘稿。
