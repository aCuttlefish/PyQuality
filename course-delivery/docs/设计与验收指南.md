# PyQuality 设计与验收指南

## 系统设计

| 环节 | 职责 | 关键产物 |
| --- | --- | --- |
| 工作台与 API | 分开接收需求、提示词、代码和函数入口，提供准备、确认和执行操作。 | 请求、可编辑的规格草案、标准确认记录。 |
| 标准管理 | 绑定需求、入口、测试计划和确认身份。改变需求或入口需要重新确认。 | 标准 ID、规格及计划摘要。 |
| 真实执行 | 编译并在受限环境运行函数，按固定断言核对结果。 | 案例状态、输入、返回值或异常、证据编号。 |
| 判定与建议 | 依据必要需求和合格证据计算功能结论，报告静态发现。模型辅助解释证据与改写提示词。 | 功能判定、质量发现、建议、适用范围和版本摘要。 |

## 关键设计决策

1. **先确认标准再执行。** 模型可辅助起草，用户依据需求和独立预期核对。确认后的标准可复用，使修复前后能在同一口径下比较。
2. **用证据决定功能结论。** 受认可的必要需求反例足以判失败。已认可范围内全过才能给范围内通过，环境阻断或证据不足时保留无法判定。通过率是描述统计。
3. **隔离运行，保留实际观察。** 容器限制权限、网络和资源。报告记录目标异常、超时及环境错误，保持这些现象可以区分。
4. **将建议与判定分开。** 模型解释和改写提示词可以变化。功能判定、案例输入、期望、实际及证据编号由固定标准和实际运行记录约束。核对修复效果时复用同一标准。

## 后续接手

增加新案例时，先写出函数入口、需求原句、输入、预期结果及其独立依据。保持同一计划执行原实现和改进实现，存下两个报告。复查失败时先定位证据不足、执行环境还是业务逻辑，再补对应测试。提示词改写的效果需用生成代码复验，应记录模型、输入、样本规模和结果范围。
