## 正文：从头直接照着读

### `[P01 · 封面]`
大家好，我是陈宏伟，今天代表我们小组汇报软件工程课设项目 **PyQuality**，成员还有彭启诚、敖德太和薛奕辰。

用一句话说清楚我们做了什么：**现在大家经常让 AI 写 Python 代码，PyQuality 就是用来帮你检查，AI 写出来的代码到底对不对、安不安全、改完是不是真修好了。**

---

### `[P02 · 为什么要做]`
为什么要做这个工具？因为大家平时用大模型写函数，最容易踩三个坑：
第一，代码能跑起来，但边界条件悄悄算错了；
第二，把代码发回给 AI 让它自己检查，它经常看漏条件，甚至编一个根本没跑过的结果；
第三，改完代码如果重新出题，就算通过数变高了，也不知道是真修好了，还是新题目变简单了。

所以我们的思路很简单：先由人确认好测试题目，把代码放进 Docker 容器里真跑一遍，改完之后用同一批题再跑一次对比。当然我们也划清了边界：只测单个 Python 函数和配套文件，不做整个网站联调，也不擅自替人改源码。

---

### `[P03 · 软件能做什么]`
具体到软件本身，我们把所有功能都收在首页这一个对话框里，打开就能做两件事。
主打功能是输入 `/accept` 验收 AI 写的函数：先聊清楚需求、生成并锁死测试用例，再丢进容器实跑、改完原题复测。
附带功能是输入 `/analyze` 体检整个 Python 项目：内置 11 项不靠大模型的静态检查，支持 30 多个快捷命令，还能导出四种格式的报告。

---

### `[P04 · 四步使用流程]`
在对话框里验收一段代码，顺着走一共就四步：
第一步，**先不贴代码**，只写一句粗略需求，或者贴你发给 AI 的提示词，系统会主动追问排序、边界和非法输入，直到把需求完全搞清楚；
第二步，系统根据明确后的需求自动生成测试用例，你逐行核对完打个勾，这批题就锁死成评判标准；
第三步，这时再把 AI 写的代码贴进来，放进 Docker 按刚才的标准实跑，直接看哪条错了、安不安全、怎么改；
第四步，改完代码点一下复测，用同一批题再跑一遍，直接看前后对比。

---

### `[P05 · 整体架构]`
接下来看看这套流程背后是怎么搭起来的。
整体尽量做轻，前端是原生 HTML、CSS 和 JavaScript，不用装 Node 也不用打包；后端用 FastAPI 搭接口，Pydantic 卡死参数格式，拉下来几分钟就能在本地跑起来。
存储上刻意拆成两块：聊天和项目存 SQLite，而测试标准和验收报告单独存成 JSON 文件，方便算哈希防篡改，也方便用户直接下载核对。哪怕没配大模型密钥，手动出题、Docker 实跑和判对错也都能正常用。

---

### `[P06 · 调用顺序与分工]`
从这张调用顺序图能看出我们怎么防止 AI 乱来。
一次验收拆成追问、出题、确认、运行几步，三方各管各的：**人负责定标准**，确认题目和答案；**AI 只负责打下手**，帮忙追问需求、起草测试、解释报错，但没有权限判通过；**程序和容器负责真跑和下结论**。

---

### `[P07 · 保证靠谱一：锁测试题]`
那么怎么保证测出来的结果靠谱？我们做了三件事。
第一件是**锁死题目不换题**。人确认标准后，系统会给需求算一个 `spec_hash`，给测试题算一个 `plan_hash`，每次运行又绑上代码的 `code_hash`。只要改了需求，旧确认立刻作废；只改代码时，就可以复用同一批题，保证一题没删、一题没改，也没法拿旧成绩冒充新代码。

---

### `[P08 · 保证靠谱二：真跑留底]`
第二件是**绝不静态猜结果，一定要真跑**。
系统会先查语法能不能编译，再按测试计划一个个传参数调用函数，把真实返回值和报错原样记下来。除了比对返回值，还内置了检查异常、检查有没有改坏原输入、检查排序等 7 种方式。如果代码超时或容器没开，会单独记为没跑成，绝不糊里糊涂算通过。

---

### `[P09 · 保证靠谱三：Docker 隔离]`
第三件是**把待测代码关进 Docker 容器里跑**。
AI 写的代码可能有死循环或危险操作，所以我们默认放进受限的 Python 3.10 容器里：右边是实测状态，无权限账号 `uid 65534`、根目录只读、断开外网、看不到本机密钥，资源限制在 1 核 CPU、512M 内存、64 个进程，死循环超时自动清理，残留容器为 0。

---

### `[P10 · 判定规则一：三态结论]`
拿到真实运行结果后，怎么判定代码对不对？判定模块 `verdict.py` 一句都不问大模型，全按死规则给出三种结论：
有语法错，或者必做要求错了一条，直接判**不通过**，哪怕 11 题对了 10 题也不放过；
测试没写全、需求含糊或者容器没跑起来，老实说**判不了**；
只有确认过的测试全部通过，才给**范围内通过**，而且明确说明只保证这批测过的输入。

---

### `[P11 · 判定规则二：功能与安全分开查]`
不过测试全过不代表就能直接上线，所以我们把“算得对不对”和“写得安不安全”分开查。
自带的 11 项静态体检不靠 AI，专门扫 `eval`、硬编码密码、坏味和复杂度。如果只是缺注释，不会把对的程序判失败，只会提示改进；但一旦扫出高危安全漏洞，就算测试全过，也会强制拦下来要求人工审查。

---

### `[P12 · 判定规则三：防止 AI 瞎编]`
最后出修改建议时，为了防止大模型胡编结果，建议里的输入、期望值和实际返回值全由程序从实跑记录里硬填进去，AI 改不了。如果 AI 把通过的题说成错了，系统会自动降级；AI 漏说的错，规则会自动补上。同时还会顺手对照需求检查原始提示词有没有写漏。

---

为了证明这个“裁判”自己没写错，我们给工具本身写了 **455 条自动化测试**，全部通过；也用真容器复跑了 5 组样例，留了 3 组真模型联调记录。

### ③ 步骤 3 复制的 GitHub Copilot 原代码（同 `demo_possibilities_original.py`）
```python
''' In this GitHub Copilot (GHC) example, the entire `possibilities` function 
    was made by GHC. The `main` function was partly written by David, but a 
    large portion was also written by GHC.

    It's also worth noting the pure ELEGANCE of the code in `possibilities`.
    It uses a recursive function to generate all possible combinations.
    Heck, this comment was also partly written by GHC.

    HUMANS NEED NOT APPLY.
'''

''' Given a target sum m, find all possible ways to make the sum with n terms.
'''
def possibilities(m, n):
    combos = []
    if n == 0:
        combos.append([])
    elif n == 1:
        if m == 0:
            combos.append([0])
        else:
            combos.append([m])
    else:
        for i in range(m+1):
            for c in possibilities(m-i, n-1):
                combos.append([i] + c)
    return combos

''' Run program.
'''
def main():

    # get inputs
    m = int(input("Target sum (m): "))
    n = int(input("Target number of terms (n): "))

    # print results
    combos = possibilities(m, n)
    print(f"Number of possibilities: {len(combos)}")
    for p in combos:
        print(p)

    return

if __name__ == "__main__":
    main()
```
