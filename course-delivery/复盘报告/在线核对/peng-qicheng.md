# PyQuality 课程项目个人复盘报告

彭启诚　3220261380　核心实现与工程测试

## 一、我的分工与人机协作

排序函数即使每次都返回空列表，也能通过“结果有序”这项检查。这个例子让我看到，验收工具本身也需要测试。我从核心实现和工程测试的角度复盘了两个容易混淆的问题：检查条件够不够，以及程序究竟有没有运行。

模型适合列出可能漏掉的输入，人负责从需求推导正确的断言。执行器记录实际输出，判定模块据此计算结果。遇到异常时，还要有人核实它出在哪一层。程序返回了错误的值、测试条件不完整、Docker 没有启动，这三种情况对应不同的处理办法。

| 项目环节 | 模型参与 | 组员或程序的工作 |
| --- | --- | --- |
| 设计 | 列出异常输入 | 按函数契约写断言 |
| 运行 | 解释报错 | 执行器保存实际输出 |
| 测试 | 整理排查步骤 | 核对容器状态和测试记录 |

## 二、三项工程取舍

（一）让判定规则可以单独测试。模型可以解释一条报错。决定用例是否通过时，我更信任可重复运行的断言：同样的需求、代码和运行证据送进判定模块，应当得到相同的结论。

（二）把运行环境写进报告。Docker 没有启动时，报告应该留下阻断原因和实际执行数。编译器已经给出的语法错误则有明确的出错位置。这两类记录分开，使用者才知道该修环境还是修代码。

（三）用错误实现反查测试是否充分。我选排序案例来检查测试的力度。把实现换成直接返回空列表，只查顺序就抓不住错误。加入元素及出现次数的检查后，用非空输入便能发现数据丢失。

## 三、一次没有运行的容器测试

v4.1 验收时，机器已经安装 Docker Desktop，但后台服务没有运行。回归用例通过了，说明系统能识别环境阻断。当时的容器实测记录仍为 NOT_RUN。到了 v4.3，项目在真实容器里运行了无限循环，观察到超时，并在结束后确认没有遗留本次任务的容器。两个版本的记录恰好说明了每次测试实际覆盖的内容。

读早期记录时，容易忽略一个细节：阻断测试本身是通过的。它检查的是 Docker 不可用时服务有没有停在正确的位置。执行数为零，报告记下阻断原因，这就满足了该回归用例的预期。可要证明容器真的隔离了运行环境，还得等 Docker 服务启动，把候选函数送进去执行。两项检查分别回答不同的问题，合在一个“通过”里，后来接手的人就会漏掉第二项。

v4.3 的实测补上了这一段。容器内报告的用户编号是 65534，根目录写入受阻，网络接口列表只有回环接口。无限循环触发超时后，再查本次任务的容器，已经没有残留。这几条记录比服务返回一次正常状态更能回答我关心的问题：代码在哪里运行，运行时拥有哪些权限，异常退出之后还有没有东西留下来。

排序用例则给了我一个检查断言的办法。设输入是 [2, 1, 1]，正确输出是 [1, 1, 2]。如果程序始终返回空列表，只比较相邻元素的顺序，就找不到逆序；即使再补一项长度检查，也抓不住同样长、元素却被替换的输出。把每个值出现的次数也纳入断言，才能把“排好序”和“原来的元素都还在”这两条要求分别落到测试上。这是我最愿意在下次代码评审里沿用的做法。

## 四、下一次我会怎么做

以后整理测试结果时，我会为真实容器运行单留一行，记下命令、环境和执行结果。这样即使单元测试全部通过，也能一眼找到仍缺少实测的环节。

写回归用例时，我会先写清楚要拦住哪一种错误，再找一份能稳定触发它的短实现。比如把总返回空列表的版本和正常排序版本都跑一遍，检查报告能否分别指出缺少元素和范围内通过。同一个测试若让这两份实现都得到好结果，就值得先改断言。
