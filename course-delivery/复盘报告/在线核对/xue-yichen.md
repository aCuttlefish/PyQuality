# PyQuality 课程项目个人复盘报告

薛奕辰　3220261418　用户体验、复现与演示

## 一、我的分工与人机协作

如果在答辩里只展示“4/7”，观众知道程序错了，却很难说出它错在哪里。换成一个具体输入就容易得多：给函数传入 AEIOU，预期是 5，页面上显示的实际结果是 0。我从第一次使用工作台的人的角度整理演示顺序，想让观众看完以后也能自己做一次这样的检查。

讲稿和步骤说明可以请模型帮助压缩，按钮名称、画面和数字要以实际页面为准。用户决定按哪些预期验收，程序记录每次运行的输入和输出。讲解的人负责把这两件事在画面上对应起来，让观众知道一个结论是怎么得出的。

| 项目环节 | 模型参与 | 组员或程序的工作 |
| --- | --- | --- |
| 准备 | 压缩讲稿 | 按页面核对按钮名称 |
| 演示 | 起草测试标准 | 用户核对预期，程序执行 |
| 复测 | 整理说明文字 | 对照两份实测报告 |

## 二、三项工程取舍

（一）把确认标准放在运行之前。元音统计要求“不区分大小写”。在点击运行前展示大写输入和对应的期望值，观众可以先作出自己的判断，也更容易理解随后看到的失败。

（二）把反例留在报告画面上。我选择 AEIOU 作演示，因为这个输入很短，观众可以直接数出五个元音。把输入、期望 5 和实际 0 放在一起，比先念一遍报告里的全部指标省事，也更清楚。

（三）第二轮沿用原来的七项测试。读完失败证据后，点击“换入示例正确实现”，再点“开始验收”。两次标准 ID 和计划摘要相同，代码摘要发生了变化，观众可以据此理解通过数为什么提高。

## 三、大写元音全部漏计

交付验证中，示例的错误实现漏掉了大写元音，七项用例只通过四项。换入正确实现后，同一计划在 Docker 中再次运行，七项全部通过。项目还做过一轮由模型生成标准的实验，经过编辑后有十项用例。两次实验检查的范围不同，所以我在演示里始终沿用七例数据，完整呈现同一次前后对照。

七个例子里，最适合放在一起看的其实是 aeiou 和 AEIOU。它们只差字母大小写，期望值都是 5。前一个通过、后一个返回 0，观众就能把问题缩小到大小写处理。再看 Hello WORLD，按需求应该数到 e、o、O，共三个。把这个例子放在纯大写字符串之后，能让人明白同一个缺陷也会影响普通的混合文本，而不只出现在刻意构造的输入上。

演示还要解释工具给出的建议怎么用。元音统计只认十个英文字母 aeiouAEIOU，七例里专门有一组带重音或其他非 ASCII 字符，预期为 0。看到“大写漏计”，直接把所有字符转成小写，看起来能处理 AEIOU；但有些字符转换后会出现英文字母和组合符号，仍有误计的可能。把这条边界用例留在复测里，观众就能看到，修好眼前的反例以后，原先通过的条件还得一起检查。

页面上“确认标准”和“开始验收”是两次点击，第一次使用时很容易把前者理解成普通的下一步。我会在这两个按钮之间稍停一下，把屏幕上的大写用例读出来。到了第二轮，再指出代码已换、标准编号相同。这样，听众能把两次点击分别对应到两个动作：先同意用什么尺子衡量，再让程序实际跑一遍。这个顺序也解释了为什么不能为修正版临时删掉难通过的用例。

## 四、下一次我会怎么做

下次修改操作说明，我希望请一位第一次打开工作台的同学独立走完演示。我只记录他在哪一步需要解释，再回头改那一步的按钮提示或讲稿。能否顺着页面找到反例并完成复测，是我最想观察的两件事。

如果安排同学试用，我会给他一个具体任务：找出哪条输入最能说明大写漏计，换入正确实现，再从报告里找到两轮用了同一套标准的依据。我会记下他在哪个页面停下来、第一次点了什么。若几个人都卡在确认框，优先改确认框旁的文字；若他们找不到实际返回值，优先调整报告里反例的位置。
