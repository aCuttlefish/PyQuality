### 决策 1  优先选择具备明确需求的可复核案例

例如扑克牌的要求可以从牌数和牌面构成检查，实际生成 56 张时有明确反例。选择这类案例能让读者独立检查输入、期望与实际结果。

> 我的实际参与、取舍依据及证据：〔填写〕

### 决策 2  在目标运行时核验边界条件

本机找到的候选边界可能无法在交付运行环境复现。电商满减应以精确十进制金额确定期望，并把触发输入放到目标 Python 容器中验证。

> 我的实际参与、取舍依据及证据：〔填写〕

### 决策 3  冻结最终计划后比较结果

探索阶段可以补测试，正式比较需明确标出计划版本。电商案例补充 M11 后，初始代码和重新生成的代码使用同一套 11 项检查，初筛结果也保留在档案里。

> 我的实际参与、取舍依据及证据：〔填写〕

### 失败案例  初筛十项通过却漏掉满减边界

电商满减实验初筛 10/10 通过，其中一组在主机 Python 3.13 发现的边界未在 Docker Python 3.10 触发。评测随后加入目标环境可复现的 M11。三项金额精确合计为 100.00 元，期望优惠后为 80.00 元，初始程序却返回 100.00 元。冻结 11 项计划后，初始代码为 10/11，使用改写提示词重新生成的版本为 11/11。这个结果说明测试设计和目标运行环境都会影响缺陷能否被发现。
